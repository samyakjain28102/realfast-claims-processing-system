## 1. The architectural spine

**[PROPOSED] Functional core, imperative shell.** The adjudication engine is a **pure function**. It
takes a claim plus a snapshot of everything needed to decide it, and returns decisions, accumulator
deltas, and traces. It performs no I/O, touches no database, and never reads the clock.

```python
def adjudicate(claim: Claim, ctx: AdjudicationContext) -> AdjudicationResult: ...
```

Everything else — loading policies, reading accumulator balances, writing decisions, wrapping it in a
transaction — lives outside it.

This is the most consequential decision in the plan, and the reasoning is worth stating because three
separate requirements collapse into it:

- **Determinism becomes structural, not aspirational.** `.cursor/rules/project.mdc` requires that the
  same inputs always produce the same decision. A pure function with an injected clock and no ambient
  state makes that a property of the design rather than a discipline we have to maintain. "Same inputs,
  same output" becomes a test we can actually write.
- **Domain tests need no database.** **[REQ]** Tests must encode domain rules, not assert HTTP status
  codes. A pure engine means a test is `adjudicate(claim, ctx)` and an assertion — no fixtures, no
  migrations, no server. Fast tests get written first, which is what the git history needs to show.
- **It's walkable under pressure.** Round two is a live extension session. "Where does the deductible
  get applied?" has one answer in one file, with no framework in the way.

The cost is real and worth naming: mapping between domain dataclasses and database rows is written by
hand rather than generated by an ORM. For a schema this size that's a contained, mechanical cost, and
it buys a domain layer with zero framework coupling.

### Layout

**[REQ]** The submission table names `app/`, so the existing empty `src/` gets renamed.

```
app/
  domain/           # pure. no imports from any layer below.
    money.py            Money value object, integer minor units
    entities.py         Member, Policy, Provider, Claim, ClaimLine
    rules.py            typed coverage rule objects
    reasons.py          reason code catalogue
    accumulators.py     generic quantity-against-limit
    engine.py           adjudicate() — the pipeline
    states.py           claim + line state machines and derivation
  application/      # use cases: orchestration + transaction boundaries
    submit_claim.py, resolve_review.py, file_dispute.py, mark_paid.py, build_eob.py
  infrastructure/   # SQLite: schema, repositories, unit of work
  api/              # FastAPI routers + pydantic request/response schemas
  seed/             # fixture data + loader
tests/
  domain/           # the bulk. pure, fast, named as domain statements
  application/      # use cases against in-memory SQLite
  api/              # the three demo flows end to end
```

The import rule is one-directional and worth enforcing consciously: `domain` imports nothing from
`application`, `infrastructure`, or `api`. If it ever needs to, something has been modelled in the
wrong place.

## 2. Domain model

### 2.1 Entities

| Entity | Key fields | Notes |
|---|---|---|
| `Member` | id, name, date_of_birth | Identity only. **No clinical data** — §3.7 of scope. |
| `Policy` | id, member_id, plan_id, effective_date, termination_date | One active policy per member. Eligibility dates only — **no deductible** (D26). |
| `Plan` | id, version, deductible, benefits[] | Versioned; the version is stamped on every decision. **`deductible` is the single source of truth** (D26). |
| `Benefit` | code, name, covered, excluded, annual_limit_amount, annual_visit_limit | A `Benefit` **is** the coverage rule (§2.2). |
| `ServiceCatalogueEntry` | service_code, description, benefit_code, scheduled_amount | Service → benefit mapping and fee schedule in one seeded table. |
| `Provider` | id, name | Deliberately thin — no network status (§3.2). |
| `Claim` | id, member_id, submitted_at, lines[] | The envelope. **`adjudication_state` and `settlement_state` are derived** (§2.6) — never stored as a `state` column. |
| `ClaimLine` | id, claim_id, line_number, provider_id, service_code, service_date, billed_amount, diagnosis_code | **Where clinical data lives**, separate from `Member`. |
| `LineDecision` | id, line_id, sequence, source, outcome, amounts, reasons[], trace, plan_version, decided_at, decided_by | **Append-only.** Amount breakdown is present only when the decision reached financial adjudication (D27). |
| `AccumulatorEntry` | id, key, quantity, decision_id, reverses_entry_id | **Append-only ledger** (§2.5). |
| `Payment` | id, claim_id, amount, paid_at, reference | Append-only, never negative. Records that money moved; no payment system behind it. |
| `Dispute` | id, line_id, disputed_decision_id, member_reason, state | Separate entity; original decision untouched. |
| `ReviewResolution` | id, line_id, dispute_id?, mode, reviewer_id, note, corrections, resulting_decision_id | The exit from review. `mode=uphold` is **dispute-only** (D28) and is recorded here, not as a `LineDecision` reason (D29). |

**[PROPOSED] Service date lives on the line, not the claim.** Real claims span dates, eligibility is
judged per service date, and accumulators are keyed by plan year. Keeping the date on the line means a
claim spanning a plan-year boundary needs no special case at all — each line simply resolves its own
plan year. Putting the date on the claim would force either a special case or a wrong answer.

**[PROPOSED] No `units` field. One line = one service occurrence.** Three physio sessions are three
lines. This looks like a small thing and isn't: with units, a visit limit that allows 2 of 5 units has
to split a line's allowed amount proportionally, which introduces division, rounding, and a rounding
policy to defend. Without units, **every amount in the system is produced by addition, subtraction, or
`min` on integers — there is no rounding anywhere.** The visit limit denies whole lines; the dollar
limit still produces the partial-payment case we want. Same domain coverage, materially less risk.

### 2.2 Coverage rules

**Decided (§7.1):** typed rule objects in code, seeded from data. Concretely, a `Benefit` is the rule —
a plan's promise about a category of service:

```python
@dataclass(frozen=True)
class Benefit:
    code: str                          # "PHYSIO"
    covered: bool                      # base case
    excluded: bool                     # explicitly excluded ≠ merely not listed
    annual_limit_amount: Money | None  # dollar cap on plan payment
    annual_visit_limit: int | None     # count cap
```

Adding a plan is a seed-data change. Adding a *new kind of rule* is a code change — which is honest,
because a new rule shape needs new logic in the pipeline and new tests regardless of how it's stored.

`covered` and `excluded` are separate fields rather than one tri-state because they produce different
reason codes with different appeal rights: "not a listed benefit" and "explicitly excluded by your
plan" are different conversations with a member.

### 2.3 The adjudication pipeline

Per line, in order. **The first gate that terminates wins**; gates 7–9 always run together as the
arithmetic stage.

| # | Gate | Failure outcome | Reason code |
|---|---|---|---|
| 0 | Claim structurally valid (claim-level; runs before anything) | Claim `REJECTED`, no lines adjudicated | `REJ_INVALID_CLAIM` |
| 1 | Service code exists in the catalogue | `NEEDS_REVIEW` | `REV_UNKNOWN_SERVICE` |
| 2 | Not a **confirmed** duplicate — an exact repeat within this claim | `DENIED` | `DEN_DUPLICATE` |
| 3 | Not a **suspected** duplicate — matches a previously adjudicated line | `NEEDS_REVIEW` | `REV_SUSPECTED_DUPLICATE` |
| 4 | Policy active on the line's service date | `DENIED` | `DEN_NOT_ELIGIBLE` |
| 5 | Benefit is covered by the plan | `DENIED` | `DEN_NOT_COVERED` |
| 6 | Benefit not explicitly excluded | `DENIED` | `DEN_EXCLUDED` |
| 7 | **Price:** `allowed = min(billed, scheduled_amount)` | no schedule entry → `NEEDS_REVIEW` | `REV_NO_PRICE` |
| 8 | **Visit limit:** visits used < limit | `DENIED` | `DEN_VISIT_LIMIT` |
| 9 | **Deductible, then dollar limit** | may be partial | see below |

Gates 0–6 are cheap checks producing clean, explainable outcomes. That ordering isn't arbitrary — it
mirrors how real adjudication sequences administrative validation before contractual eligibility before
pricing, and it means we never compute money for a claim that was never going to pay.

**Rejected vs denied** are deliberately different claim states. `REJECTED` means the claim was never
adjudicated because it was incoherent; `DENIED` means it *was* adjudicated and the answer was no. A
member can dispute a denial; there's nothing to dispute about a malformed submission.

### 2.4 The arithmetic, and the thing it gets right

```
allowed            = min(billed, scheduled_amount)
above_allowed      = billed - allowed                          → member owes
deductible_applied = min(allowed, deductible_remaining)        → member owes
after_deductible   = allowed - deductible_applied
plan_paid          = min(after_deductible, limit_remaining)    → plan pays
denied_amount      = after_deductible - plan_paid              → member owes
```

**Invariant, enforced as a property test on every decision that reached pricing / financial
adjudication (gates 7–9):**

```
billed == above_allowed + deductible_applied + plan_paid + denied_amount
```

Money is never created or destroyed by adjudication; it is only assigned to a party. If that assertion
ever fails, a priced decision is wrong — and it will catch an entire class of arithmetic bug the
example-based tests would miss.

**[DECIDED] Pre-pricing exits have no financial breakdown** (D27). Claim `REJECTED`, `NEEDS_REVIEW`, and
denials that terminate before pricing (gates 0–6) do not carry `allowed` / `above_allowed` /
`deductible_applied` / `plan_paid` / `denied_amount`. The conservation test does not apply to them.
`payable` sums `plan_paid` only from current decisions that have a breakdown.

**The outcome is a coverage determination, not a payment amount.** This is the single most important
modelling point in the pipeline, and it comes straight from the research:

| Outcome | Condition |
|---|---|
| `APPROVED` | The whole allowed amount was covered — **even if `plan_paid` is zero** because it all went to the deductible |
| `PARTIALLY_APPROVED` | Some of the allowed amount was covered, some denied (the dollar-limit boundary) |
| `DENIED` | None of it was covered |
| `NEEDS_REVIEW` | The rules could not decide |

A line where the entire allowed amount lands on the deductible is **approved and paid zero**. Calling
that a denial would be wrong in the domain, wrong on the member's EOB, and would wrongly grant appeal
rights. This distinction is why `outcome` and the amount breakdown are separate concepts rather than
one field.

**[DECIDED] The annual dollar limit caps plan payment, not allowed amount.** The deductible portion
does not consume the benefit's annual limit. A benefit maximum limits the *insurer's* exposure, and the
deductible is the member's own money — charging a member's own spending against the plan's cap would
exhaust the benefit faster than the plan actually promised.

**[DECIDED] One deductible per policy per plan year**, shared across all benefits. The common real
design, and it produces the more interesting interaction: a physio claim consumes the deductible that
then changes the outcome of a later diagnostics claim. Per-benefit deductibles would be more machinery
demonstrating less, since benefits would never affect each other.

**[PROPOSED] In a reimbursement model, `above_allowed` is the member's cost.** Worth flagging because
it inverts the research: with a provider contract, billed-minus-allowed is a write-off the provider
absorbs and the member never sees. We reimburse members directly, so there is no provider contract to
absorb it — if the member paid ₹500 and the plan allows ₹300, the member is ₹200 out of pocket. Same
arithmetic, different liability party, and the explanation must say so honestly.

**Multi-line ordering, and the working balance.** Lines are adjudicated in `line_number` order,
ascending, and **the engine threads a running accumulator balance through them as it goes.**

This is load-bearing, not bookkeeping. The snapshot passed into the engine is the *starting* balance,
not a constant to be re-read per line. Two ₹4,000 lines on one claim against ₹2,000 of remaining limit
must pay ₹2,000 in total: the first line consumes the remainder, and the second sees zero available and
is denied. If each line were evaluated against the same untouched snapshot, both would pay ₹2,000 and
the limit would be overspent — a single-threaded bug with no database anywhere near it, and the exact
same failure as the concurrency race in §4.1 wearing different clothes.

Fixed ordering is what makes the threading well-defined. "Which line got the last ₹2,000" must not
depend on dict iteration order, so the rule is stated, and tested, rather than emergent.

### 2.5 Accumulators

**[DECIDED] Append-only ledger, not a mutable counter.**

```python
@dataclass(frozen=True)
class AccumulatorKey:
    member_id: str
    plan_year: int
    scope: Scope          # DEDUCTIBLE | BENEFIT_AMOUNT | BENEFIT_VISITS
    benefit_code: str | None
```

Balance is the sum of entries for a key. Every entry references the decision that caused it. Reversing
is posting a compensating entry, never deleting.

The generic shape matters: an accumulator is **a quantity against a limit**, where the quantity is money
or a visit count. Building it as a money counter and bolting counts on later is exactly the retrofit
scope.md §3.2 warned about.

Why a ledger rather than a counter, given it's more work:

- **Appeals need reversal.** When an overturned decision replaces an earlier one, the earlier one's
  consumption must be undone. With a counter that's a read-modify-write that can drift or double-apply;
  with a ledger it's an append that's arithmetically impossible to get half-done.
- **The trace needs before/after.** Scope requires accumulator state before and after in every
  explanation. A ledger has it by construction; a counter has to remember to capture it.
- **It matches the immutable-decision story.** Decisions are append-only; if their financial effects
  were mutable, the audit trail would only be half honest.

The cost is a `SUM` per key per adjudication. At this scale that is not a consideration.

**Accumulator posting rules (D16).** Be precise — this is not "no consumption until resolution":

| Line outcome | When ledger entries post |
|---|---|
| `NEEDS_REVIEW` or `UNDER_APPEAL` | **Never** — no ledger entries while in these states |
| Terminal (`APPROVED`, `PARTIALLY_APPROVED`, `DENIED`) | When that decision becomes current — on **initial submit** if terminal from the start, or after **review/dispute resolution** if re-adjudication produces a terminal outcome |
| Re-adjudication after resolution | **Reverse** superseded terminal entries (compensating append); **post** entries for new terminal outcomes — **one transaction** (D19). Lines still in review post nothing |

Terminal **sibling** lines on a mixed claim therefore **do** consume on initial submit even while another
line is in `NEEDS_REVIEW`. Only the review/appeal line withholds consumption.

### 2.6 State machines

**Line item**

```
PENDING ──adjudicate──> APPROVED | PARTIALLY_APPROVED | DENIED | NEEDS_REVIEW
NEEDS_REVIEW ──resolve──> APPROVED | PARTIALLY_APPROVED | DENIED
any terminal ──dispute──> UNDER_APPEAL ──resolve──> APPROVED | PARTIALLY_APPROVED | DENIED
```

**Claim** — **[DECIDED]** two derived lifecycles, not one. Full reasoning in `domain-model.md` §3.2.

```
adjudication_state   (derived from line states)
  RECEIVED ──validate fails──> REJECTED                        (terminal)
  RECEIVED ──adjudicate──>  any line NEEDS_REVIEW/UNDER_APPEAL → UNDER_REVIEW
                            all lines DENIED                   → DENIED
                            all lines APPROVED                 → APPROVED
                            otherwise                          → PARTIALLY_APPROVED
  APPROVED | PARTIALLY_APPROVED | DENIED ──line disputed──> UNDER_REVIEW

settlement_state     (derived from append-only Payment rows vs payable)
  payable == 0   → NOTHING_DUE
  paid < payable → DUE
  paid == payable→ SETTLED
  paid > payable → OVERPAID          (anomaly: surfaced, never auto-corrected)
```

Neither field is ever assigned directly; both are recomputed from append-only data. A payment may only
be recorded when `adjudication_state` is `APPROVED` or `PARTIALLY_APPROVED` **and** `settlement_state` is
`DUE` — we never pay a claim still under review.

The single chain in the problem statement (`… → approved/denied → paid`) breaks on a member disputing a
denied line after the claim was paid: the plan then owes more on a claim in a terminal state. Splitting
the axes makes that case need no special handling — adjudication reopens while settlement stays
`SETTLED`, and if the appeal succeeds, `payable` rises and settlement becomes `DUE` on its own.

Money only moves forward: `Payment` rows are append-only and never negative (scope §5).

### 2.7 Reason codes

**[PROPOSED]** Our own catalogue, CARC-informed, with each code carrying three attributes beyond its
message: **category**, **who absorbs the amount**, and **whether it is appealable**.

| Code | Liability | Appealable |
|---|---|---|
| `INFO_COVERED` — covered and paid | plan | — |
| `MEM_DEDUCTIBLE` — applied to your deductible | member | no |
| `MEM_ABOVE_ALLOWED` — billed above the plan's allowed amount | member | no |
| `DEN_NOT_ELIGIBLE` — no active policy on the date of service | member | yes |
| `DEN_NOT_COVERED` — not a benefit under this plan | member | yes |
| `DEN_EXCLUDED` — explicitly excluded by this plan | member | yes |
| `DEN_ANNUAL_LIMIT` — annual benefit maximum reached | member | yes |
| `DEN_VISIT_LIMIT` — annual visit limit reached | member | yes |
| `DEN_DUPLICATE` — confirmed duplicate of another line on this claim | member | yes |
| `REV_UNKNOWN_SERVICE` — unknown service code / `REV_UNKNOWN_BENEFIT` — service maps to a benefit not defined on this plan / `REV_NO_PRICE` / `REV_SUSPECTED_DUPLICATE` | — | — |
| `REJ_INVALID_CLAIM` | — | — |

There is **no** `HUM_UPHELD` reason code (D29). An uphold is a `ReviewResolution` event; the
`LineDecision` it produces keeps the deterministic RULES reason (e.g. `DEN_EXCLUDED`).

The appealable flag is what lets the dispute endpoint reject an appeal against a deductible with a real
explanation instead of a validation error.

### 2.8 Explanation and trace

Every decision carries an ordered trace — one entry per gate evaluated:

```json
{ "step": "annual_dollar_limit", "rule": "BENEFIT.PHYSIO.annual_limit_amount",
  "plan_version": 3, "inputs": {"after_deductible": 40000, "limit_remaining": 10000},
  "result": "partial", "accumulator_before": 90000, "accumulator_after": 100000 }
```

The member-facing message is rendered from the reason code; the trace is the evidence underneath it.
Both are produced by the engine at decision time — not reconstructed later, which would let them drift
from what actually happened.

## 3. Disputes and review resolution

One endpoint, two modes (D16, D21). Manual financial overrides are **out of scope**.

**Correct facts and re-adjudicate.** Reviewer supplies corrected facts on affected line(s) → **whole claim**
re-adjudicated against **original `plan_version`** (D18) → new `LineDecision` records with
`source=RULES`. If fact correction changes an accumulator key (e.g. plan year), reverse prior entries
atomically before posting new ones (D19).

**Uphold (dispute-only, D28).** Reviewer closes an **open dispute** without fact changes → whole claim
re-adjudicated → original outcomes confirmed with the same RULES reason codes → `ReviewResolution`
records `mode=uphold` → dispute record closed. Uphold on a `NEEDS_REVIEW` line with no dispute is
**rejected** — that line can only exit via fact correction (D25).

**Iterative resolution (D23).** `POST /reviews/{line_id}/resolve` accepts **multiple attempts** with
updated facts until all lines under review reach terminal outcomes, or the reviewer upholds (dispute).
Each call records a `ReviewResolution`. The claim stays `UNDER_REVIEW` while any line remains
`NEEDS_REVIEW` or `UNDER_APPEAL`.

**Each attempt appends decisions (D24).** Every re-adjudication pass appends new `LineDecision` rows
(incrementing `sequence`) — **including** when a line **remains** `NEEDS_REVIEW`. Each record carries
the current reason code, trace, and corrected inputs. Prior decisions stay immutable.

**Still `NEEDS_REVIEW` after correction (D25).** No in-scope escape: try again with different facts, or
(on dispute) uphold. **Closing as permanently undecidable** without a terminal rules outcome is **future
work** — not implemented in this take-home.

**[DECIDED] What may a reviewer correct?** Facts only:

| Correctable | Never correctable |
|---|---|
| `service_code`, `service_date`, `provider_id`, `billed_amount`, `diagnosis_code` | `allowed_amount`, `deductible_applied`, `plan_paid`, `denied_amount`, `outcome`, reason codes |

**[DECIDED] Accumulator behaviour on resolution:** reverse ledger entries from **superseded terminal**
decisions, then post entries for **new terminal** outcomes — all in one transaction (D19). Lines in
`NEEDS_REVIEW` or `UNDER_APPEAL` never post entries, including after a re-adjudication pass that leaves
them still in review.

**Not in scope (D21, D25):** manual financial overrides; close review as permanently undecidable without
a rules-derived terminal outcome. Both are future scope.

## 4. Persistence

**[DECIDED] Plain `sqlite3` from the standard library, with a hand-written `schema.sql` and thin
repositories.**

| Option | For | Against |
|---|---|---|
| **stdlib `sqlite3` + `schema.sql`** (proposed) | Zero dependencies; the schema is a readable artifact we can point at from `docs/domain-model.md`; explicit transactions; no mapper config between pure dataclasses and rows | Hand-written row mapping, more lines of plumbing |
| SQLAlchemy Core | Schema as Python, portable, less SQL by hand | A dependency and an abstraction to explain live, for a schema of ~10 tables |
| SQLAlchemy ORM | Least plumbing | Pulls persistence concerns into entities, or forces a second set of models — either way it fights the pure-domain decision in §1 |

Since the domain is already pure dataclasses, an ORM's main benefit — not writing mapping code — is the
one thing that would compromise the design. The plumbing cost is accepted deliberately.

### 4.1 Concurrency: not overspending a limit

Two claims for the same benefit, adjudicated at the same time, against ₹2,000 of remaining annual limit.
Both read ₹8,000 consumed, both conclude ₹2,000 is available, both pay it. The plan pays ₹12,000 against
a ₹10,000 limit and the accumulator is now permanently wrong for that member. This is the write-skew
race, and it is the single most damaging bug this system could ship: it produces a wrong number quietly,
which is exactly what `.cursor/rules/project.mdc` exists to prevent.

**Correct outcome:** whichever claim commits first is partially approved — ₹2,000 paid, ₹2,000 denied as
`DEN_ANNUAL_LIMIT`. The second is fully denied for the same reason. The plan pays exactly ₹10,000.

**[DECIDED] Take the write lock before reading the balances.** That inversion is the whole fix:

```python
conn.execute("PRAGMA journal_mode=WAL")
conn.execute("PRAGMA busy_timeout=5000")

conn.execute("BEGIN IMMEDIATE")     # declare write intent up front
balances = read_accumulators(...)   # safe: no other writer can be active
result  = adjudicate(claim, ctx)    # pure, no I/O
write_decisions_and_ledger(result)
assert_within_limits(result)        # closing invariant, below
conn.execute("COMMIT")
```

SQLite permits exactly one write transaction database-wide, and its documentation states the guarantee
plainly: once `BEGIN IMMEDIATE` succeeds, no subsequent operation in that transaction will fail with
`SQLITE_BUSY`. Claim B's transaction therefore cannot begin until A commits, so B reads ₹10,000
consumed rather than ₹8,000 and denies its line correctly.

The default `BEGIN DEFERRED` is what would break us. It opens read-only and attempts to upgrade at the
first write, which under WAL fails with `SQLITE_BUSY_SNAPSHOT` — and `busy_timeout` deliberately does
*not* retry that error, because retrying would silently discard the other writer's intervening change.
Declaring write intent up front converts a failure into a wait.

**Two layers on top, both cheap:**

- **Closing invariant.** Before commit, assert that no accumulator balance exceeds its limit. If one
  does, roll back, pay nothing, route the line to `NEEDS_REVIEW`. This is the safety rule applied to our
  own concurrency control: if the locking is ever wrong, the system stops rather than paying wrong.
- **Retry by full re-adjudication.** If `BEGIN IMMEDIATE` times out, re-run the entire adjudication
  against fresh balances — never patch the previous result, because the correct answer genuinely differs
  once the other claim has committed. This is safe precisely because `adjudicate()` is pure and has no
  side effects, which is a direct payoff from §1.

**Deliberately not built: per-accumulator row locking or optimistic version columns.** With one writer
database-wide, serialising whole adjudications *is* the correct granularity; a version check would be
redundant machinery. The equivalent on a real database — `SELECT ... FOR UPDATE` on the accumulator key,
or a version column with a conditional update — is recorded here so the migration path is stated rather
than rediscovered.

**The limitation that remains is throughput, not correctness.** Every adjudication serialises against
every other, including ones touching unrelated members and benefits. Correct, and unscalable. The
trade-off is recorded as an assumption in `docs/decisions.md` §4, along with the productionisation path —
the short version being that the correctness mechanism (ledger, invariant, pure retryable engine) is
already portable, and only the *locking granularity* would change.

**Determinism is not violated by order-dependence.** The accumulator balance is an *input* to
adjudication, so "same inputs, same output" still holds — two concurrent claims receiving different
answers is correct behaviour. What matters is that the ordering is *recorded* rather than accidental,
and the ledger's entry sequence provides it: we can always explain why claim A received the last ₹2,000
and claim B did not.

**Cross-claim duplicate detection stays out of the engine.** The application layer queries prior
adjudicated line keys and passes them into `AdjudicationContext`. The engine remains pure, and duplicate
detection is still testable without a database.

**[DECIDED] Confirmed duplicates and suspected duplicates are different things, and the model keeps
them apart.**

| Case | Outcome | Reason code | Why |
|---|---|---|---|
| **Confirmed** — an exact repeat within the same claim (same service code, service date, provider) | `DENIED` | `DEN_DUPLICATE` | A single claim listing the same service twice is a data error, not a clinical event. Deterministic and safe to automate. |
| **Suspected** — the same match against a previously adjudicated line on another claim | `NEEDS_REVIEW` | `REV_SUSPECTED_DUPLICATE` | Identical details across submissions may still be legitimate repeated care — a bilateral procedure, two sessions the same day. |

Real payers auto-deny the second case. We deliberately don't: auto-denying it means confidently
refusing to pay for care that may well have happened, which is precisely the silent wrong answer the
safety rule exists to prevent. The ambiguity is escalated rather than guessed.

The distinction is carried in the vocabulary, not just the outcome. A **confirmed** duplicate is a
statement of fact the system can make on its own; a **suspected** duplicate is a question the system
raises for a human. Collapsing them into one "duplicate" concept would lose exactly the information a
reviewer needs — and would make a guess look like a finding.

This is a documented departure from industry practice, and `docs/decisions.md` should say so plainly
rather than let a reviewer assume we didn't know the convention.

## 5. API

FastAPI, pydantic schemas at the boundary only — domain dataclasses never leak into HTTP.

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/claims` | Submit; adjudicates synchronously; returns the full decision set |
| `GET` | `/claims/{id}` | Claim, line decisions, amounts, explanations, trace |
| `GET` | `/claims?member_id=` | List — shows accumulator effects across claims |
| `GET` | `/claims/{id}/eob` | Member-facing summary |
| `POST` | `/claims/{id}/lines/{n}/disputes` | File a dispute (rejects non-appealable reasons) |
| `POST` | `/reviews/{line_id}/resolve` | Correct facts + re-adjudicate, or uphold (**dispute-only**) |
| `POST` | `/claims/{id}/payments` | Record a payment; advances `settlement_state` |
| `GET` | `/members/{id}/accumulators` | Balances per benefit and plan year |

Synchronous adjudication on submit: no queues, no background workers. The system is small enough that
asynchrony would be architecture for its own sake, and a synchronous response makes the demo legible.

**PHI:** no member names, diagnosis codes, or claim contents in logs or error messages — identifiers
only. Cheap, and it's the most common real leak.

## 6. Testing

**[REQ]** Tests first, visible in git history, encoding domain rules.

| Layer | What | Speed |
|---|---|---|
| `tests/domain/` | The bulk. Pure engine, table-driven, no DB | milliseconds |
| `tests/application/` | Use cases against in-memory SQLite — transactions, reversal, state recomputation | fast |
| `tests/api/` | The three demo flows end to end | a few |

Named as domain statements, not mechanics:

```python
def test_line_at_annual_limit_boundary_pays_remainder_and_denies_the_rest(): ...
def test_line_fully_absorbed_by_deductible_is_approved_and_paid_zero(): ...
def test_overturned_denial_consumes_the_annual_limit(): ...
def test_duplicate_line_within_a_claim_is_denied(): ...
def test_earlier_line_number_wins_the_last_of_an_annual_limit(): ...
def test_two_lines_on_one_claim_cannot_together_exceed_the_annual_limit(): ...
```

Three beyond example-based tests:

- **Money conservation** (§2.4, D27) as a property test over generated claims **that reached pricing**.
  Pre-pricing outcomes are out of the invariant. Catches arithmetic bugs no example test would find.
- **Determinism**: adjudicating identical inputs twice yields byte-identical decisions and traces. This
  is the safety rule expressed as an executable check.
- **Concurrency** (§4.1), threaded, in `tests/application/`: two claims submitted simultaneously against
  the same remaining limit. Assert that total plan payment never exceeds the limit and that exactly one
  claim is partially approved. This one is worth the awkwardness of a threaded test — it is the only
  thing that actually demonstrates the correctness claim the docs make, and without it we would be
  asserting a guarantee we never exercised.

## 9. Where judgement is still needed during the build

Not open decisions — places where the plan could go wrong in implementation and needs attention:

- **The accumulator must be generic from the first line of code** (§2.5). Building it as a money counter
  and adding visit counts later is the one retrofit in this plan that would be genuinely expensive.
- **A limit can be overspent in two different ways** — by two lines on one claim (§2.4) and by two
  concurrent claims (§4.1). They look like different problems and have different fixes, but they are the
  same mistake: treating a balance that is being consumed as if it were a constant. Getting one right
  does not get the other right.
- **Reversal on appeal is the highest-risk code path** (§3). It is the only place decisions are
  superseded, and a missed reversal corrupts every later claim for that member — silently.
- **The money-conservation invariant should be written early** (§6, D27), not after the arithmetic is
  finished. It applies to priced decisions only. It's the cheapest safety net available and it only
  helps if it exists while the arithmetic is being built.
